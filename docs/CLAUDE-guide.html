Moussa Shop — guide du CLAUDE.md

État au 16 octobre 2026, branche develop.

Ce document explique, avec des schémas, les règles écrites dans le fichier CLAUDE.md à la racine du projet. Le CLAUDE.md reste en Markdown : c'est lui que Claude lit automatiquement au début de chaque session. Cette page sert aux personnes : comprendre pourquoi chaque règle existe.

Résumé en 6 points
  1. Commandes : JDK 21 dans ~/.jdks, tests UI lancés avec Edge, pas de Python.
  2. Méthode : un point du docs/TODO.md = code + tests + compte rendu + un commit, puis le point suivant.
  3. Architecture : en couches web → service → repository, les entités ne sortent jamais du service, l'API ne parle qu'en DTO.
  4. SOLID : services à une seule responsabilité, injection par constructeur, Strategy plutôt qu'un switch qui grossit.
  5. Argent et quantités : BigDecimal avec arrondi explicite, jamais de double.
  6. Discipline : pas de pattern « au cas où », pas de refactoring hors du point en cours, chaque règle métier a son test.

1. À quoi sert le CLAUDE.md

Claude ne garde aucun souvenir d'une session à l'autre. Le CLAUDE.md est relu à chaque démarrage : c'est la « fiche d'accueil » du projet. On y met uniquement ce qu'on ne peut pas deviner en lisant le code.

Figure 1 — Le CLAUDE.md remplace l'explication qu'on donnerait à un nouveau développeur.
Ce qu'on y met
  • commandes qu'on peut copier telles quelles
  • pièges propres à la machine (JDK, Edge)
  • règles chiffrées et vérifiables
Ce qu'on n'y met pas
  • la liste des fichiers (Claude sait les lire)
  • des généralités (« écrire du code propre »)
  • des textes longs : chaque ligne coûte du contexte

3. Façon de travailler

Le docs/TODO.md est traité point par point, en boucle, sans attendre de validation entre deux points. L'utilisateur relit l'ensemble à la fin.

Figure 2 — Cycle d'un point du TODO.

Pourquoi un commit par point ? Chaque commit raconte une seule fonctionnalité : facile à relire, facile à annuler (git revert) si un point pose problème, sans toucher aux autres.

4. Architecture backend

Le backend est organisé en couches. Chaque couche ne parle qu'à celle du dessous. C'est l'organisation actuelle du code (web/, service/, repository/, entity/) : la règle demande de la garder propre, pas de la changer.

Figure 3 — Les couches et leurs dépendances. Les flèches vont toujours vers le bas.
CoucheFaitNe fait jamais
web/Valider l'entrée, appeler un service, convertir en DTOCalculer un prix, ouvrir une transaction, appeler un repository
service/Règles métier, transactions, orchestrationConnaître HttpServletRequest ou les DTO web
repository/Lire et écrire en baseContenir une règle métier
entity/Représenter les données persistéesÊtre renvoyée telle quelle par l'API
À éviter : logique dans le contrôleur
@PostMapping("/sales")
Sale create(@RequestBody Sale s) {
  s.setTotal(s.getQty() * s.getPrice());
  return saleRepository.save(s);
}
Attendu : contrôleur mince
@PostMapping("/sales")
SaleResponse create(@Valid @RequestBody
                    CreateSaleRequest req) {
  return saleService.checkout(req);
}
Et l'architecture hexagonale ? Elle n'est pas imposée. Migrer 50 services d'un coup laisserait le code à moitié en couches, à moitié hexagonal, ce qui est pire que l'un ou l'autre. On en garde l'idée utile : les ports. Tout ce qui touche l'extérieur (fichiers, réseau, horloge) passe par une interface, pour pouvoir le remplacer par un faux dans les tests. Si un jour on veut aller plus loin, on le fait sur un module isolé (license/ ou backup/), comme point dédié du TODO.

5. SOLID appliqué

Cinq principes, chacun traduit en règle concrète pour le projet.

SResponsabilité unique

Un service = une raison de changer. Au-delà de ~300 lignes, on découpe.

Ex. : PurchaseCosting (coût d'achat) séparé de CostingService.

OOuvert / fermé

Ajouter une variante = ajouter une classe, pas modifier un switch.

Ex. : un nouveau moyen de paiement ne touche pas le code des anciens.

LSubstitution de Liskov

Toute implémentation respecte le contrat de son interface.

Signe d'erreur : une méthode qui lance UnsupportedOperationException.

ISégrégation des interfaces

Des interfaces petites, ciblées sur un besoin.

Mieux deux interfaces de 2 méthodes qu'une de 12.

DInversion des dépendances

Injection par constructeur, champs final. Dépendre d'interfaces pour l'extérieur.

Pas de @Autowired sur les champs.

Exemple : injection par constructeur (D)

À éviter
@Service
class StockService {
  @Autowired
  private ProductRepository repo;
}

Dépendance cachée, impossible à fournir dans un test sans Spring.

Attendu
@Service
class StockService {
  private final ProductRepository repo;
  StockService(ProductRepository repo) {
    this.repo = repo;
  }
}

Dépendance visible, objet immuable, testable avec un simple new.

6. Design patterns

Un pattern n'est utile que s'il résout un problème présent. La figure 4 sert de guide de décision.

Figure 4 — Choisir un pattern selon le besoin.

Strategy plutôt qu'un switch qui grossit

Figure 5 — Ajouter un moyen de paiement = ajouter une classe. Rien d'existant n'est modifié (principe O). Noms donnés à titre d'illustration.

Value Object pour l'argent

À éviter
double total = 0.1 + 0.2;
// 0.30000000000000004

Le double ne sait pas représenter exactement 0,1 : les écarts s'accumulent sur les caisses et les rapports.

Attendu
BigDecimal total = new BigDecimal("0.1")
    .add(new BigDecimal("0.2"))
    .setScale(2, RoundingMode.HALF_UP);
// 0.30

Exact, avec un arrondi choisi et écrit noir sur blanc.

7. Règles générales

RèglePourquoi
Méthodes courtes, vocabulaire de la boutique (vente, sortie, approvisionnement, unité)Le code se lit comme le métier ; un nom clair évite un commentaire.
Pas de null en retour : Optional ou exception métierSupprime les NullPointerException surprises et rend l'absence explicite.
Exceptions métier dédiées, un seul @RestControllerAdviceToutes les erreurs HTTP ont le même format, à un seul endroit.
Chercher avant d'écrire (util/, service/)Une règle de calcul dupliquée finit toujours par diverger.
Chaque règle métier a son test, nommé par comportementLe nom du test (sortieValoriseeAuPrixDeVente) documente la règle.
Pas de refactoring hors du point en coursUn point du TODO reste un petit commit relisible ; les améliorations repérées vont dans le compte rendu.

8. Angular

Figure 6 — Les composants affichent, les services de core/ pensent et parlent au serveur.
  • Composants standalone, sans logique métier ni appel HTTP direct.
  • Types stricts dans models/, jamais de any : les erreurs apparaissent à la compilation, pas chez le client.
  • Désabonnement automatique (takeUntilDestroyed, pipe async) : pas de fuite mémoire quand on change d'écran.

9. À ne pas faire

✗ Commiter sur master

On travaille sur develop ; master reçoit les versions livrées.

✗ Modifier une migration livrée

Elle a déjà tourné chez les clients. On en ajoute une nouvelle dans bootstrap/, avec son test.
